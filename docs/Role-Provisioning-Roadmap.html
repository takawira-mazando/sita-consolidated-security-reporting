How tenancy binds to the path: the JWT carries department_ids / branch_ids / province_ids. scope_covers requires the target scope to be a subset of the caller's scope, and tenant_filter turns that scope into SQL filters on every data query — so a branch-admin on treasury-budget can only create users inside treasury-budget, and those users only ever see treasury-budget data. A province scope expands to the province's full department set on both sides (provincial_departments_for_province), provincial departments (113) have no branch subtree, and a whole-estate (empty) scope is reachable only via a nationwide role.

The Full Path — Step by Step

  1. 1
    operator (managed-service creator — Hosi Technologies) creates the SITA superuser — role admin, scope national. It can also create a peer operator for rotation, and nothing else.
  2. 2
    admin (SITA superuser) creates the department superusers — dept-admin (scope: its department), province-dept-admin (scope: its province), branch-admin, transversal-admin — and provisions national-level dashboard access (exec, compliance, sre, blue arrows). It cannot create a peer admin or operator.
  3. 3
    dept-admin cascades inside its own department — creates branch-admins (branch-admin, scope: one branch) and the operational roles, all dept-scoped. It can never reach another department.
  4. 4
    branch-admin lands on the finest / lowest tier — creates the operational users (soc · appsec · dbsec, plus province-soc-lead · local-appsec) scoped to exactly its branch. These are leaves: they grant nothing further, and their dashboard data is tenant-filtered to the branch.

How to read this matrix: delegation is strictly one-way down the tenancy tree — a tier can only create roles beneath it and only inside its own scope. "Cannot create" is enforced by can_manage (target role must be in the caller's GRANTABLE_ROLES and sit strictly below the caller's tier) plus scope_covers (target scope must be a subset of the caller's scope). Three exceptions are explicit: operator ↔ operator and transversal-admin ↔ transversal-admin peer rotation, and the sre nationwide user-management path (ops users only). Every account created is provisioned from the HR pool (person_id) with an email that must match the HR record.

The Full User-Creation Path — End to End

  1. 1
    Admin signs in with real credentials (POST /auth/login) → JWT carries roles + tenant scope (dept / branch / province ids). backend/app/api/routers/auth.py · verify_token
  2. 2
    Users & RBAC opens (GET /admin/users — requires admin_read, filtered by scope_covers to the caller's subtree only). frontend AdminUsersPage.tsx · backend/app/api/routers/admin.py
  3. 3
    Pick the HR employee — search the HR pool (GET /admin/persons); accounts exist only for hr.employees linked to identity.persons. No external / free-form accounts.
  4. 4
    Choose roles + scope — the modal only lists roles in GRANTABLE_ROLES for the caller's tier; the scope picker is limited to the caller's subtree.
  5. 5
    Create — POST /admin/users enforces _validate_scope + can_manage (role ≤ caller tier, role grantable, scope ⊆ caller scope) → 403 otherwise. Email must equal the HR record's email.
  6. 6
    New user signs in (POST /auth/login) → gets its role's dashboard (exec / soc / appsec / dbsec / compliance / sre).
  7. 7
    Tenant-filtered data — every query runs through tenant_filter(claims): a branch-scoped soc sees only its branch's findings / alerts / risks. Nothing else in the estate leaks in.
