THE GAP

Role-gated, but not role-aware

RBAC today decides which screen you land on. It does not shape what the words are permitted to say.

A provincial reader and a national reader of the same dashboard receive identical text.

The agent pipeline

Every request passes two gates before any row is read

POST /api/v1/reports-ai/generate JWT → claims │ ├─ GATE 1 · RBAC require_report_permission("executive_briefing") │ permission = report_ai:<report_type> │ DEFAULT-DENY — absent role gets NOTHING │ ├─ GATE 2 · TENANCY resolve_report_scope(claims) → ReportScope (frozen) │ scope_hash = sha256(canonical scope tuple) │ ├─ RETRIEVAL scope is FIRST POSITIONAL arg on every accessor │ delegates to tenant_filter() — never re-implemented │ empty scope → expression.false() → FAIL CLOSED │ ├─ DISCLOSURE every fact tagged TENANT_SCOPED | ESTATE_WIDE │ ├─ FACT PACK pure builder + fact_pack_hash │ identical pack feeds BOTH the model and the fallback │ ├─ PROMPT ◄── THE POINT allowed_claim_classes INJECTED FROM THE ROLE │ temperature 0.2 · constrained narrative_html │ model receives facts only — no DB, no SQL, no tools │ └─ VERIFY ① every numeral grounded in the fact pack ② claim filter — DISCARD unheld-class sentences ③ scope_hash match across envelope + cache + audit any failure → deterministic template, NEVER model text
Role-aware prompting · the core of the request

A second RBAC layer, applied to the text not the request

A role may be permitted to request a report but not to see everything inside it. ClaimClass governs what the caller's role may see named in the generated narrative.

An exec reads "Estate risk is 62, critical exposure concentrated in 4 applications". A soc reads "CVE-2026-31429 on payment-gateway, alert a1b2…, owner Payment Ops".

Today the platform differentiates by which dashboard you land on. This differentiates by what your narrative is permitted to say. That contrast is demo item 5.
Prompt assembly · G2 §8

The prompt states the restriction. The verifier enforces it.

constraints: figures_only_from_facts: true allowed_claim_classes: - headline_metrics - risk_buckets - app_names - department_names - aggregate_compliance # ▲ INJECTED FROM THE CALLER'S ROLE estate_wide_attribution: required output: schema: narrative_html temperature: 0.2

Enforcement is discard, never warn. A failed verification returns the deterministic template — never the model text. Richard's adversarial suite runs on day 6, and every attempt must fail at the verifier. That is demo item 8.

WHY THIS IS THE ANSWER

Satisfies G2 §12(6) directly — no SaaS LLM, self-hosted, with sovereign cloud available later as DR behind the same redaction gate.

Zero CAPEX, zero lead time. R01 (GPU/hosting slip, Critical 16) does not apply to this window. There is nothing to procure and no budget cycle to enter.

Reversibility is cheap. gateway.py is an httpx client against an OpenAI-compatible endpoint. Moving to sovereign cloud or on-prem GPU later is configuration, not a rewrite.

A 3B model on CPU is sufficient. The claim is not prose quality — it is that a role-aware prompt yields role-appropriate text over correctly scoped facts, and that the verifier catches what the model gets wrong.

R20 — the model is not yet pulled. A ~2 GB download sits on the critical path. If it fails, the fallback serves the same fact pack and therefore the same numbers, and the demonstration degrades to a template report. That degradation is pre-agreed — it is why the fallback was kept in the same scope rather than deferred.

Decision D2 · the most consequential item on the agenda

There is no code path that will ever scope them

Both compliance tables carry no tenancy columns — 8 and 10 columns respectively, neither with department_id or branch_id. Not a better filter, not a different query. The columns do not exist.

OptionConsequence
Declare ESTATE_WIDE 684 rows, labelled estate-wide, disclosed in every generated response, enforced by the verifier. THE ONLY CONTROL AVAILABLE
Add tenancy columns A warehouse programme: columns, backfill of historical rows, a tenancy source of truth for pre-existing snapshots, migration rehearsal, AG sign-off. Changes the reporting core.
Infer tenancy at query time Rejected. Guessing the scope of a snapshot that predates the tenancy model is guessing. A guessed scope in a compliance figure is worse than a declared absence of scope.
And it is now generated text. An unlabelled estate-wide figure inside a model-written narrative is materially worse than in a fixed dashboard string — the reader cannot tell it was authored under different rules. Disclosure is no longer good practice; it is the only thing standing between a generated report and an undeclared estate-wide disclosure.
Response envelope · attribution is part of the contract

Not metadata. Mandatory fields.

{ "report_type": "compliance_status", "narrative_html": "<h3>Estate compliance posture</h3>…", "authorisation": { "granted_by_role": "exec", "permission": "report_ai:compliance", "scope_class": "estate_wide", "scope_hash": "sha256:1a99b011a25ec26e", "departments_in_scope": 173, "claim_classes_applied": ["headline_metrics", "risk_buckets", "app_names", "department_names", "aggregate_compliance"] }, "disclosure": [ { "scope_class": "estate_wide", "source": "compliance_snapshots", "rows": 456, "reason": "no tenancy columns on table" } ], "provenance": { "model_id": "qwen2.5:3b", "model_digest": "sha256:…", "prompt_id": "executive_briefing", "prompt_version": 1, "latency_ms": 6120 }, "verification": { "numerals_checked": 47, "ungrounded": 0, "claims_violations": 0, "passed": true }, "fallback_used": false }
A generated security report must be attributable to the exact model and prompt that produced it — or it is not evidence. scope_hash appears in the response, the cache key and the audit row, equal in all three. authorisation and disclosure are mandatory; neither is optional.
