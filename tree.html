🗃 sita-platform — security pipeline architecture & reporting interface

📦 Bridging the gap: Synthetic OEM feed & live cutover approach & plan

🔴 The problem — no live OEM data feed yet

The platform must ingest from four OEM sources — HCL AppScan, Imperva DAM/WAF, the API Security platform, and compliance CSV feeds. Live access (API credentials / tenant access) is not available yet, which blocks end-to-end ingestion, pipeline verification, and report development if we wait.

🟢 The approach — a deterministic synthetic OEM feed that mirrors real connector output

Instead of waiting, we built a synthetic feed generator that emits payloads shaped exactly like each real OEM connector’s poll() output, so every downstream stage — staging → normaliser → warehouse → alert/risk/compliance engines → REST API → dashboards — runs and is tested before live access exists.

PiecePathWhat it provides
Feed generatorbackend\app\synthetic\generator.pySyntheticOEMFeed — deterministic (seed=42) per-source generators: appscan_finding, imperva_dam_event, imperva_waf_event, apisec_endpoint, compliance_row; batch()/sample()
Fixture datasetbackend\tests\fixtures\5 JSON fixtures (3 records each) with a loader (__init__.py) — OEM-shaped IDs (ASC/DAM/WAF/API-2026), severities, CVSS/CVE, ISO timestamps — used by the test suite
Seed pipelinebackend\app\entrypoints\seed_simulated.pyCLI that generates realistic volumes, writes staging.batch_runs/raw_records, runs the normaliser → warehouse upsert → alerts → risk scores → connector health, all offline
Config-driven mappingbackend\app\processing\field_mapper.yamlJSONPath field maps + severity maps per source (incl. apisec exposure thresholds) — the same map the live connectors will use
Testsbackend\tests\28 pytest cases (normaliser / alert engine / risk engine) proving the pipeline from fixtures through to alerts — CI runs them

🔖 Why the synthetic feed is safe to build on

  • Field-shape parity — the generator’s record shapes mirror the connector contracts (see backend\app\connectors\{appscan,imperva,apisec,compliance}.py), so switching to live data is a source swap, not a rewrite.
  • Deterministic & replayable — fixed seed means reproducible fixtures and stable test expectations.
  • Downstream untouched — everything after staging.raw_records consumes JSONB payloads regardless of producer; reports never read staging directly.
  • Test-gated — the same normaliser/config/tests that validate synthetic data validate live data, so regressions surface immediately on cutover.

🔗 The data flow (synthetic today — identical topology with live)

SyntheticOEMFeed → seed_simulated.py → staging.raw_records → Normaliser → warehouse.findings → Alert / Risk / Compliance Engines → warehouse.* → REST API → Report UI

🔋 How we plug in the live feed to replace the synthetic one

Live cutover reuses the exact connectors already built (appscan.py, imperva.py, apisec.py, compliance.py) — the synthetic feed exists only because those can’t authenticate yet. The switch is a source swap at the ingestion boundary:

  1. Provision live access — obtain OEM credentials / tenants and store them in backend\.env / connector config (AppScan API-key login, Imperva token, API-Security key, compliance file drop).
  2. Run the real connector in test mode — execute one authenticate() → poll() per source and inspect the raw payload. This validates auth, pagination and rate-limit behaviour (the live-OEM-blocked items #1 / #4).
  3. Diff against fixtures — compare a live raw_payload to the fixture JSON for the same source; confirm the normaliser (field_mapper.yaml) maps it without schema changes.
  4. Toggle the producer — point entrypoints\ingestion.py at the real connector instead of SyntheticOEMFeed; both write identical shapes to staging.raw_records, so processing/dispatch/reporting need no changes.
  5. Watch batch runs — confirm a real batch lands in staging.batch_runs and flows to warehouse.findings; verify connector health flips to healthy and DLQ stays empty.
  6. Calibrate weights & WAF rules — recalibrate risk-engine weights and enable the live WAF block feed (US-APPSEC-04) using real volume, then re-run the test suite.
  7. Keep synthetic as sandbox — retain SyntheticOEMFeed behind a flag (e.g. SEED_MODE=simulated) for demos, CI and training; live becomes the default once validated.

Status: synthetic feed & fixtures shipped, 28 tests green, CI running pytest. Blocked on live OEM access for E2E connector auth/pagination, risk-weight calibration, and the WAF block feed.

🛠️ Why the backend was built on FastAPI & Python backend framework rationale

🟢 Why FastAPI + Python

The backend (connectors, ingestion, normaliser, alert/risk/compliance engines, dispatch, and the REST API) is one Python service built on FastAPI with SQLAlchemy ORM and PostgreSQL.

  • Async-native pipeline — FastAPI is built on asyncio, so long-running OEM poll() calls, retries, circuit breakers, and rate limiting don’t block the event loop while alerts are still being served.
  • Automatic OpenAPI docs — every endpoint in backend\app\api\routers\ is self-documented at /docs from type hints — free, accurate API contract for the frontend to consume.
  • Pydantic validation — schemas in backend\app\api\schemas\ enforce request/response shapes at the boundary, so bad payloads fail fast instead of corrupting the warehouse.
  • One language for the whole pipeline — connectors, normaliser, engines and API share types, config (config.py), logging (monitoring\logging.py) and metrics (monitoring\metrics.py), so there is no cross-language impedance between stages.
  • Ecosystem for data work — SQLAlchemy async sessions, Alembic migrations, pandas for normalisation (normaliser.py), YAML-driven rules — all first-class in Python.

📈 Advantages that matter here

AdvantageHow it serves this platform
Concurrent OEM pollingAsync connectors poll HCL AppScan, Imperva, API-Security, compliance in parallel without thread pools or blocking the API.
Type-safe contractsPydantic schemas + OpenAPI keep the frontend’s typed API clients honest at every release.
Declarative configfield_mapper.yaml, alert_rules.yaml, app_catalog.yaml drive mapping/rules/enrichment without code changes.
Observability built inPrometheus /metrics + structured logs feed the Grafana dashboard with near-zero wiring.
Fast startupNo heavy framework machinery; containers in docker-compose.yml come up in seconds for demos.

Bottom line: FastAPI is the strongest choice for this platform because the entire pipeline is Python — connectors, normaliser, engines and API share one runtime, one type system, and one toolchain. There is no framework more suited to a security-pipeline service that must poll OEMs asynchronously, transform data with pandas, and serve a typed, documented REST contract.

💻 Why the frontend was built on React, TypeScript & Vite frontend stack rationale

🟢 Why React + TypeScript + Vite

The reporting UI (frontend\) is a single-page app: React 18 + TypeScript + Vite, with axios API clients and six role-gated dashboards. No server-side rendering — it is served as static files by nginx and talks to the FastAPI backend over /api/v1/*.

  • Component reuse across six dashboards — StatCard, Panel, Gauge, MiniBarChart, BarRow, Chip, OemTag in frontend\src\components\dashboard\ are shared by Exec, SOC, AppSec, DbSec, Compliance and SRE views — one source of truth for each visual.
  • TypeScript end-to-end — the typed API modules (src\api\*.ts) mirror the backend’s Pydantic/OpenAPI schemas, so a field rename surfaces as a compile error, not a runtime blank chart.
  • Hooks encapsulate data access — useExecData, useSocData, … built on useApi/usePolling keep each page declarative and testable.
  • Vite for speed — instant dev-server HMR and fast production builds keep the dashboard iteration loop tight.

📈 Advantages that matter here

AdvantageHow it serves this platform
Six dashboards, one component kitRole pages compose the same widgets; new roles reuse them instead of forking markup.
Contract-first safetyTS types in src\types.ts + src\api\ make the API boundary explicit and refactor-safe.
Live "Explain this dashboard"explanations.ts + ExplainOverlay.tsx build narratives from live API facts — no hardcoded figures to drift.
Zero sample data in UIEvery number comes from PostgreSQL via FastAPI; the UI can never disagree with the warehouse.
Fast, dependency-lightVite bundles only what each page imports; custom CSS charts (no chart lib imported) keep it lean.

Bottom line: React + TypeScript + Vite is the strongest choice for this reporting UI because it delivers a type-safe, componentised, role-gated SPA that mirrors the FastAPI contract exactly — six dashboards composed from one shared widget kit, with every number proven to come from PostgreSQL.
