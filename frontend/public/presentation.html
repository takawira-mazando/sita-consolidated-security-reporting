Strategic Context & National Mandate

The Challenge: Fragmented Telemetry & Audit Overhead

Before this platform, government cybersecurity data was siloed across multiple tools, proprietary consoles, and independent department networks, creating critical blind spots for national leadership.

CHALLENGE 01

Siloed OEM Security Tools

AppScan SAST/DAST, Imperva WAF, and Imperva/Thales DAM generated distinct data models with zero cross-correlation, preventing holistic risk posture calculation.

CHALLENGE 02

Cross-Tenant Leakage Risk

Multi-department sharing was blocked by POPIA and sensitive state data restrictions. No architectural mechanism existed to allow provincial benchmarking without exposing raw asset logs.

CHALLENGE 03

Auditor-General Compliance Burden

Manual audit attestation packs required hundreds of hours per department. No tamper-evident cryptographic verification was available to validate historical compliance claims.

Internal Key, Not a Government Key

identity.users.person_id stays an internal UUID. A government identifier is an attribute of an account, never its primary key — so a corrected or reissued PERSAL number never forces an account re-key or rewrites audit history.

Guard Rails at the Boundary

  • 13-digit identity numbers rejected as employment identifiers, validated by date prefix + Luhn check digit
  • Ambiguity is never guessed — an unrecognised shape is surfaced, not coerced into a scheme
  • Duplicate PERSAL refused rather than reassigned between people
  • 2,451 person records mirrored, each carrying a scheme-qualified identifier

Regulatory Integrity & Attestation

Auditor-General (AG) Export: ECDSA Digital Signatures

Eliminating audit manual overhead with aggregation-only attestations, signed ECDSA NIST P-256 and verifiable offline against a published public key — no trust in the database required.

ECDSA_P256_SHA256 · SECP256R1

Asymmetric Signature Verification

Every attestation from /api/v1/exports/ag-compliance is hashed and digitally signed. The signed bytes and the signature are stored beside the hash, so verification is a real signature check rather than a database-existence test.

"signing_algorithm": "ECDSA_P256_SHA256",
"key_id": "baa30ac535769463",
"integrity_hash": "8a1e038b6139c6...a28d374",
"policy_version": "ag-export-v2",
"scope_hash": "6f2a91c0...e4d7",
"valid": true,
"reason_code": "signature_valid"

Three independent checks, all required: re-hashing the stored bytes reproduces the recorded hash; the ECDSA signature validates over exactly those bytes; the record is complete. Any one failing yields valid: false — a missing signature is a failure, never a pass.

OFFLINE VERIFIABLE · NO TRUST REQUIRED

Cryptographic Properties

  • Public key published at /exports/ag-compliance/public-key as X.509 SubjectPublicKeyInfo PEM — an auditor verifies with the public key alone, never the signing key.
  • Key fingerprinting: SHA-256 over the DER public key; the first 16 hex chars are the key_id, so a verifier can detect key rotation after the fact.
  • Reproducible: no wall-clock value inside the signed bytes, so identical data yields an identical hash and an identical signature.
  • All-or-nothing verification across every row carrying a hash — one forged record fails the whole attestation rather than being skipped by first-match.
  • Append-only ledger: UPDATE/DELETE/TRUNCATE rejected at the database, plus a guard that fails loudly if the trigger is ever disabled.
  • Scope-bound: each record binds actor, role, policy version and scope hash, so it answers who, under what authority, at which version.

POPIA & Privacy Safeguards

  • Aggregation-only by construction: the signed body carries control status/severity distributions and scope metrics — never raw findings, exploit payloads or per-asset rows.
  • Identity numbers encrypted at rest with AES-256-GCM at the column layer; masked on every output path via a single central PII policy.
  • Access-audited: exports, tenant switches, privilege changes and reads of person records each append a signed row.
ENCRYPTION AT REST & KEY CUSTODY

Data Protection Controls

  • Identity numbers encrypted at rest with AES-256-GCM, applied transparently at the column layer — a database dump no longer exposes them. The GCM tag is bound to the column, so a ciphertext moved between employees' rows fails to decrypt rather than authenticating silently.
  • Signing keys are static in production. The platform refuses to start rather than mint an ephemeral attestation key that would change every deploy and silently invalidate prior attestations.
  • Transport is separate and explicit: TLS 1.3 at the edge; session tokens are HS256 JWTs, distinct from the ECDSA attestation key.
  • Scope is not legal compliance. A verifiable signature proves an attestation was not altered; it is not evidence that the underlying controls are effective, nor that POPIA s.57 authorisation has been obtained.
  • Residual: the rest of the person record — name, work phone, email, clearance — is personal information but not encrypted at rest; minimisation and output masking are the controls there.
